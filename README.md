# PR Review Agent

An automated code review assistant for GitHub pull requests. It reads a PR's diff, flags real bugs/security/dependency/style issues with severity ratings, and lets you decide what actually gets posted as comments.

This repo is itself a Claude Code **plugin** (`.claude-plugin/plugin.json` + a local `.claude-plugin/marketplace.json`), installable with:

```
/plugin marketplace add "<path to this repo>"
/plugin install pr-review@pr-review-tools
```

## What's in this repo

- `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` — the plugin manifest and a local marketplace entry so it can be installed as above.
- `skills/pr-review-setup/` — the `/pr-review-setup` skill: checks `gh` is installed and authenticated, asks for the target repo (an existing local clone path, or a URL/`owner-repo` to clone) and a coding-standards path, and writes `repo.config.json`. Run this once per project before using `/pr-review`, or any time you want to repoint it.
- `skills/pr-review/` — the `/pr-review` skill (the "conductor": lists PRs, asks questions, posts comments).
- `agents/pr-reviewer.md` — the `pr-reviewer` agent (the "reviewer": reads the diff and writes findings).
- `docs/coding-standards/` — bundled default TypeScript/React rules (e.g. `RX-011`, `TS-003`) used when a project doesn't supply its own `coding_standards_path`.
- `repo.config.json` — generated by `/pr-review-setup`: which repo to review, its local clone path, and (optionally) a custom coding-standards path.
- `userConfig.coding_standards_dir` in `plugin.json` — an optional personal default coding-standards folder (set/changed with `/plugin configure pr-review@pr-review-tools`), used by `/pr-review-setup` as a suggested default across all your projects.
- `project_code/` — default location for repos cloned by `/pr-review-setup`.
- `pr_review/` — one Markdown report per reviewed PR, containing the findings as JSON.

## How the flow works

Think of it as two roles working together: a **conductor** (the skill) that talks to you and to GitHub, and a **reviewer** (the agent) that actually reads code. The conductor never reviews code itself, and the reviewer never touches GitHub except to read.

0. **First time in a project:** run `/pr-review-setup`. It checks `gh auth status`, asks whether to use an existing local clone or clone a repo for you, asks where your coding standards live (or use the bundled defaults), and writes `repo.config.json`.
1. **You say "review PRs"** (or `/pr-review`, or "review this PR").
2. **Conductor figures out which repo.** It reads `repo.config.json` to get the repo, local clone path, and coding-standards path, unless you named a repo directly — if `repo.config.json` is missing or `gh` isn't authenticated, it runs `/pr-review-setup` first.
3. **Conductor lists open PRs** on that repo and shows them to you as a table.
4. **You pick one PR.** Only one at a time — no batch reviewing.
5. **Conductor hands that PR to the reviewer agent.** This is where the real work happens:
   - The agent pulls the PR's title/body/SHAs from GitHub, then gets the actual code diff from the **local clone** (fast, no GitHub API token-burning).
   - It reads the diff hunk by hunk, plus the project's own coding standards and the house TypeScript/React rules, looking only for things that matter: bugs, security holes, risky/unused dependency changes, and standards violations. It skips nitpicks and personal-taste stuff.
   - Every finding gets a severity (`high` / `medium` / `low`) based on real impact, plus a concrete suggested fix.
   - If a past review of this PR exists, the agent carries forward which findings were already posted, so nothing gets flagged as "new" twice.
   - It writes everything to `pr_review/pr-<number>-<date>.md` as a JSON block — it never posts anything itself.
6. **Conductor shows you the findings**, grouped high → medium → low, each with file/line, description, suggested fix, and whether it's already posted.
7. **You choose what to post.** The conductor asks (always, every time) which findings — if any — should become real PR comments. You can also write your own custom comment instead.
8. **Conductor posts your selections** as inline PR review comments (never approves/requests-changes — comments only), de-duplicating against anything already posted, and updates the report file so the posted state sticks around for next time.
9. **You're asked if you want to review another PR.** If yes, back to step 4.

## Why it's split this way

- **Separation of concerns:** the agent is the only thing that reads code and judges it; the skill is the only thing that talks to the human and to GitHub's write API. That keeps "what's wrong with this code" and "what do we do about it" as separate decisions.
- **Nothing gets posted without a human saying so.** The agent's output is always just a file on disk until you explicitly approve a comment.
- **Local-first:** using a cloned copy of the target repo for diffs/standards avoids slow, token-heavy GitHub API calls — `gh` is only used for things that truly require it (PR metadata, posting comments).
- **State survives across runs:** because reports are saved per PR with posted/not-posted status, re-running a review later won't re-post the same comment twice.
